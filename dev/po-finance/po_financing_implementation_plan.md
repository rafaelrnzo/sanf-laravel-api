# PO Financing Implementation Plan

## 1. System Objective

Build a digital PO Financing / Standby Financing disbursement flow that allows customers to submit financing requests through the system, from plafond checking to final disbursement.

The target end-to-end flow is:

```text
Check plafond
→ Select supplier
→ Input invoice / PO
→ Select tenor
→ Select transfer account
→ Submit required documents
→ Internal / SISCA validation
→ Generate SPT / Transfer Request Letter
→ Generate realization document
→ Customer signature / e-sign
→ Internal signature / e-sign
→ Final verification
→ Disbursement
```

Main objectives:

```text
Reduce manual document submission
Control required documents
Lock plafond during active submission
Prevent duplicate invoice submission
Make SPT and realization documents traceable
Support e-signature and manual signature
Support document expiry and resubmission
```

---

## 2. Feature Scope

### 2.1 Customer Side

Customers should be able to:

```text
1. Log in to the system
2. View active plafond
3. Select SBF / PO Financing plafond
4. Select supplier under the selected plafond
5. Input invoice / PO data
6. Select tenor
7. Select transfer bank account
8. Upload required documents
9. Preview PO summary
10. Generate / confirm SPT
11. Submit disbursement request
12. View disbursement status
13. Sign / e-sign realization document
14. Resubmit realization document if expired or revised
```

### 2.2 Internal / SISCA Side

Internal users should be able to:

```text
1. Receive customer submissions
2. View submission details
3. Validate invoice / PO
4. Validate documents
5. Validate supplier
6. Validate plafond
7. Approve, reject, or reroute the request
8. Generate realization document
9. Request customer signature
10. Perform internal e-signature if required
11. Perform final signed document verification
12. Trigger disbursement
13. Release plafond if rejected, cancelled, or expired
```

## 3. Required Documents

### 3.1 Mandatory Initial Documents

```text
1. SPT / Transfer Request Letter
2. Invoice / PO
3. Document that verifies the Invoice / PO
```

### 3.2 Conditional Documents

```text
1. Giro
   Required if payment method is giro
   or if the plafond configuration requires giro

2. Customer-signed realization document
   Required after the request is approved

3. Internal-signed realization document
   Required if internal e-signature is part of the flow

4. Additional supporting documents
   Required based on supplier, plafond type, or internal policy
```

## 4. SPT Document Recommendation

### 4.1 Recommended Decision

The SPT should be generated by the system instead of being fully uploaded manually.

Reasons:

```text
Transfer amount can be locked
Supplier can be locked
Destination bank account can be locked
Invoice / PO can be locked
Tenor can be locked
Audit trail is safer
Risk of manual document modification is reduced
```

### 4.2 SPT Flow

```text
Customer fills in disbursement form
→ System validates data
→ System generates draft SPT
→ Customer previews SPT
→ Customer confirms SPT
→ Customer signs / e-signs SPT
→ SPT is locked
→ Request can be submitted
```

### 4.3 Data Required in SPT

```text
customer_id
customer_name
plafond_number
supplier_id
supplier_name
invoice / PO number
invoice amount
total disbursement amount
currency
destination bank account
bank name
account number
account owner
tenor
tenor type: daily / monthly
request date
due date
```

### 4.4 Important Rule

```text
SPT must not be manually edited after customer confirmation.
If amount, supplier, bank account, or tenor changes, the old SPT must be voided and a new SPT must be generated.
```

## 5. Detailed Customer Flow

## Step 1 — Check Plafond

Customer opens the PO Financing menu.

Existing API references:

```text
GET V2/plafond/:cust_id
GET api/plafond/list_sbf
```

System displays:

```text
plafond type
plafond number
total plafond
used plafond
ongoing invoice amount
remaining plafond
expiry date
active suppliers
```

Validations:

```text
If plafond does not exist → block process
If plafond is expired → block process
If remaining plafond <= 0 → block process
If plafond code is not SBF / PO Financing → block process
```

---

## Step 2 — Select Plafond

Customer selects one active plafond.

Existing API reference:

```text
GET api/plafond/detail_sbf/{plafond_number}
```

System retrieves:

```text
plafond_number
cust_id
total plafond
used plafond
ongoing invoice amount
remaining plafond
expiry date
supplier list
```

Validations:

```text
Selected plafond must belong to the logged-in customer
Plafond must be active
Current date must be less than or equal to expiry date
```

---

## Step 3 — Select Supplier

Customer selects supplier from the supplier list under the selected plafond.

Supplier data should include:

```text
supplier_id
supplier_name
active_period
minimum_disbursement_tenor
maximum_disbursement_tenor
tenor_type
currency_id
```

Validations:

```text
Supplier must exist under the selected plafond
Supplier must be active
Invoice currency must match supplier / plafond currency
Customer tenor must be within supplier minimum and maximum tenor
```

Recommended MVP rule:

```text
1 request = 1 supplier
```

This keeps the first version safer because the process does not support split transfer.

---

## Step 4 — Input Invoice / PO

Customer inputs:

```text
invoice / PO number
invoice / PO date
currency
amount
invoice / PO file upload
```

Existing API reference:

```text
POST api/standby_financing/check_invoice
```

Existing payload example:

```json
{
  "nomor_invoice": "1234567890",
  "total_invoice": 500000,
  "noplafond": "62505004136"
}
```

Additional validations required:

```text
Invoice number must not already exist in another active request
Invoice amount must be greater than 0
Invoice date must not be later than the current date
Invoice currency must match supplier / plafond currency
Total invoice amount must not exceed remaining plafond
Invoice must not already be ongoing
```

Invoice statuses to check:

```text
draft
submitted
pending_review
approved
disbursed
rejected
cancelled
expired
```

Invoice can only be reused if previous status is:

```text
rejected
cancelled
expired and plafond has been released
```

## Step 5 — Select Tenor

Customer inputs tenor.

Validation:

```text
tenor >= minimum_disbursement_tenor
tenor <= maximum_disbursement_tenor
```

If supplier `tenor_type = Daily`:

```text
Tenor is calculated in days
period_end = period_start + tenor days
```

If supplier `tenor_type = Monthly`:

```text
Tenor is calculated in months
period_end = period_start + tenor months
```

Fields to store:

```text
tenor
tenor_type
period_start
period_end
due_date
```

## 8. Realization Document Resubmission

This is a critical gap that needs to be handled.

Current problem:

```text
There is no system support for resubmitting a realization document that has already been printed.
```

Solution:

```text
Add resubmit realization document feature
Add regenerate realization document feature
Add manual signed realization document upload
Add old realization document voiding
```

### Scenario A — Realization Document Expires Before Customer Signature

```text
REALIZATION_GENERATED
→ AWAITING_CUSTOMER_SIGN
→ EXPIRED
→ customer requests regeneration
→ internal approves regeneration
→ system voids old document
→ system generates new document
→ customer signs again
```

### Scenario B — Customer Already Printed the Document but Uploads After Expiry

There are two policy options.

#### Safer Option

```text
Expired document cannot be used
Customer must download and sign a newly generated document
```

#### Flexible Option

```text
Customer may upload the old signed document
However, it must go through manual verification
Internal user must approve or reject it
```

Recommended option:

```text
For financing flow, use the safer option.
Expired document is invalid and must be regenerated.
```

Additional states:

```text
REALIZATION_EXPIRED
REALIZATION_REGENERATE_REQUESTED
REALIZATION_REGENERATED
REALIZATION_SUPERSEDED
```

## 10. Plafond Locking Plan

Plafond locking is mandatory to prevent over-financing.

### 10.1 Draft State

```text
Plafond is not locked yet
```

### 10.2 Submitted State

```text
Request amount is moved to ongoing invoice amount
Available plafond is reduced
```

Formula:

```text
available = total_plafond - used_plafond - ongoing_invoice_amount
```

### 10.3 Rejected State

```text
ongoing invoice amount is reduced by request amount
state = REJECTED
```

### 10.4 Cancelled State

```text
ongoing invoice amount is reduced by request amount
state = CANCELLED
```

### 10.5 Disbursed State

```text
ongoing invoice amount is reduced
used plafond is increased
state = DISBURSED
```

### 10.6 Expired Realization Document

Recommended policy:

```text
Realization document expiry does not immediately release plafond.
Give a grace period.
After the grace period ends, auto-cancel the request and release the plafond.
```

## 18. Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Duplicate invoice submission | Over-financing | Unique invoice validation |
| Plafond is not locked | Over limit | Lock plafond at submission |
| SPT is manually modified | Fraud / mismatch | Generate SPT from system |
| Expired realization document is still used | Invalid document | Expiry + void + regenerate |
| E-signature is incomplete | Legal risk | Customer and internal signer matrix |
| Giro is not uploaded | Missing required document | Conditional document rule |
| Reroute to existing system fails | Request stuck | Reroute status + retry mechanism |
| Customer uploads old document version | Wrong document version | Document versioning + hash |

## 19. Acceptance Criteria

### 19.1 Customer Submission

```text
Customer cannot submit if required documents are incomplete.
Customer cannot submit if invoice is duplicate.
Customer cannot submit if tenor is outside minimum / maximum range.
Customer cannot submit if total amount exceeds remaining plafond.
Customer cannot submit if supplier is not part of the selected plafond.
Customer cannot split transfer into more than one bank account.
```

### 19.2 Internal Review

```text
Internal user can approve, reject, or request revision.
Rejected request must release locked plafond.
Approved request must continue to realization document generation.
Every action must be recorded in audit trail.
```

### 19.3 Realization Document

```text
Realization document must have an expiry date.
Customer cannot sign an expired document.
Expired document can be regenerated.
Old document must become superseded or void.
```

### 19.4 E-signature

```text
Customer signature must be recorded.
Internal signature must be recorded if required.
Final document is valid only if all required signers have signed.
```

### 19.5 Disbursement

```text
Disbursement can only be processed if final document is valid.
Plafond changes from locked to used after disbursement.
Customer can view final disbursement status.
```

## 21. Final Recommendation

The flow can be implemented safely if the following components are treated as core controls:

```text
state machine
plafond lock
document versioning
system-generated SPT
realization document expiry

```

Without these controls, the process may still work functionally, but it will not be safe enough for a financing workflow.
